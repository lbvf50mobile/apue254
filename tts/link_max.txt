LINK MAX "SC LINK MAX" defines the maximum number of hard links that can
point to a single file's inode within a single filesystem [The Open Group].
Each hard link is simply an additional directory entry referencing the same
underlying inode number, sharing the file's data blocks and metadata, with the
file being physically deleted from the filesystem only when its link count
drops to zero. While the POSIX XSI standard mandates a historical minimum
baseline of just 8 hard links per file [The Open Group], real-world
filesystems diverge sharply: ext4 hardcodes a 16-bit link counter, capping at
65,535 links per file, while XFS uses a 32-bit counter with no practical fixed
ceiling—only the available inode space limits it. In daily systems
programming, attempting to create a hard link beyond the filesystem's
threshold causes the link or linkat system calls to immediately fail with
the classic "JE eM LINK" error, meaning \"Too many links.\" For Ruby and Go
developers, this boundary rarely surfaces in typical application code where
File.link or os.Link are used sparingly, but becomes a critical constraint in
infrastructure engineering: backup systems like rsync with link dest,
snapshot tools, and deduplication engines that aggressively create hard links
to save disk space can silently hit this ceiling when consolidating hundreds
of thousands of identical configuration files or log entries into a single
archive directory.
