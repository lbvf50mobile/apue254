number of bits used to represent file sizes in bytes
FILESIZEBITS (_SC_FILESIZEBITS) defines the number of bits the operating system uses to represent file sizes in bytes [The Open Group]. On modern 64-bit Linux and macOS architectures, this value is universally 64, theoretically allowing individual files to reach exabyte scales. However, on legacy 32-bit systems, this limit was historically 32, imposing a hard ceiling of 2GB (signed) or 4GB (unsigned) per file. In daily systems programming, attempting to manipulate a file that exceeds this bit-width boundary without Large File Support (LFS) causes kernel system calls like stat(), fstat(), or lseek() to abruptly fail with the classic EOVERFLOW (Value too large for defined data type) error. For Ruby and Go developers, this is largely transparent on modern 64-bit environments—where File.size or os.Stat seamlessly handle massive files—but becomes a critical deployment trap when running 32-bit containers or legacy binaries. In those constrained environments, processing multi-gigabyte logs or datasets will crash unless the underlying runtime or C-extensions are explicitly compiled with large file offsets enabled (e.g., the _FILE_OFFSET_BITS=64 macro in C).
_SC_FILESIZEBITS
maximum number of hard links to a single file
LINK_MAX (_SC_LINK_MAX) defines the maximum number of hard links that can point to a single file's inode within a single filesystem [The Open Group]. Each hard link is simply an additional directory entry referencing the same underlying inode number, sharing the file's data blocks and metadata, with the file being physically deleted from the filesystem only when its link count drops to zero. While the POSIX/XSI standard mandates a historical minimum baseline of just 8 hard links per file [The Open Group], real-world filesystems diverge sharply: ext4 hardcodes a 16-bit link counter, capping at 65,535 links per file, while XFS uses a 32-bit counter with no practical fixed ceiling—only the available inode space limits it. In daily systems programming, attempting to create a hard link beyond the filesystem's threshold causes the link() or linkat() system calls to immediately fail with the classic EMLINK error, meaning "Too many links." For Ruby and Go developers, this boundary rarely surfaces in typical application code where File.link or os.Link are used sparingly, but becomes a critical constraint in infrastructure engineering: backup systems like rsync with --link-dest, snapshot tools, and deduplication engines that aggressively create hard links to save disk space can silently hit this ceiling when consolidating hundreds of thousands of identical configuration files or log entries into a single archive directory.
_SC_LINK_MAX
maximum number of bytes on a terminal’s canonical input queue
MAX_CANON (_SC_MAX_CANON) defines the maximum number of bytes in a canonical (line-editing) input line that the terminal driver is guaranteed to buffer before delivering it to the reading process . While POSIX/XSI mandates a historical minimum of 255 bytes , and Linux publicly defines MAX_CANON as 255 in its headers , the practical limit on Linux has long been the line discipline's internal read buffer, N_TTY_BUF_SIZE, which is 4096 bytes . This means the kernel can actually accept and edit canonical lines up to 4096 bytes despite the nominal 255-byte guarantee . Exceeding this boundary causes the kernel to discard input in excess of the limit until a newline is received . For Ruby and Go developers, this constraint is rarely encountered directly because high-level libraries like Readline or bufio typically manage terminal input through non-canonical or buffered modes, making MAX_CANON relevant only when writing low-level terminal utilities that interact directly with termios.
_PC_MAX_CANON
number of bytes for which space is available on terminal’s input queue
MAX_INPUT (_SC_MAX_INPUT) defines the maximum number of bytes that can be queued in the terminal's input buffer before the reading process consumes them, with POSIX mandating a historical minimum of 255 bytes. While Linux publicly defines MAX_INPUT as 255 in accordance with POSIX, the tty line discipline internally uses a 4096-byte read buffer (N_TTY_BUF_SIZE), meaning the kernel can physically queue more input than the nominal MAX_INPUT guarantee before data loss occurs. Exceeding this boundary causes the terminal driver to discard excess data until a line termination is received, or block further writes depending on the flow-control configuration. For Ruby and Go developers, this constraint is rarely encountered because high-level libraries like Readline or bufio typically manage input buffering at the application layer, making MAX_INPUT relevant only for low-level terminal utilities that interact directly with termios or handle rapid, unprocessed keystroke streams.
_PC_MAX_INPUT
maximum number of bytes in a filename (does not include a null at end)
NAME_MAX (_SC_NAME_MAX) defines the maximum number of bytes in a single filename component, excluding the terminating null character [The Open Group]. While the POSIX/XSI standard mandates a historical minimum of just 14 bytes, modern Linux filesystems like ext4 and XFS typically enforce a 255-byte limit—though some stacked or network filesystems impose tighter constraints, such as ecryptfs's 143-character cap. Attempting to create, rename, or open a file with a name exceeding this boundary causes system calls like open() or mkdir() to immediately fail with the classic ENAMETOOLONG error. For Ruby and Go developers, this constraint is generally transparent until hitting edge cases like generating temporary files from long hashes or URLs; in such scenarios, methods like File.open or os.Create will raise an Errno::ENAMETOOLONG or syscall.ENAMETOOLONG exception, requiring developers to explicitly truncate or hash the filename to stay within the filesystem's byte limit.
_PC_NAME_MAX
maximum number of bytes in a relative pathname, including the terminating null
PATH_MAX (_SC_PATH_MAX) defines the maximum number of bytes in a pathname, including the terminating null character [The Open Group]. While the POSIX standard mandates a minimum acceptable value of 256 bytes for _POSIX_PATH_MAX, modern Linux systems typically enforce a 4096-byte limit as defined in kernel headers. Attempting to resolve or manipulate a file path that exceeds this boundary causes system calls like open(), stat(), or getcwd() to immediately fail with the classic ENAMETOOLONG error. For Ruby and Go developers, this constraint is generally transparent, but it surfaces as a critical edge case when dealing with deeply nested directory structures, such as legacy node_modules or complex temporary file hierarchies; in these scenarios, methods like File.open or os.Open will raise an Errno::ENAMETOOLONG or syscall.ENAMETOOLONG exception, forcing developers to explicitly shorten path components or restructure the directory layout.
_PC_PATH_MAX
maximum number of bytes that can be written atomically to a pipe
PIPE_BUF (_SC_PIPE_BUF) defines the maximum number of bytes that can be written to a pipe or FIFO in a single write() call such that the operation is guaranteed to be atomic, meaning it will not be interleaved with data from other concurrent writers [The Open Group]. While the POSIX standard mandates a minimum of 512 bytes, modern Linux kernels enforce a 4096-byte limit (matching the system memory page size). If a single write() exceeds this boundary, the kernel drops the atomicity guarantee: data from multiple processes may become scrambled, or, in non-blocking mode, the call may perform a partial write. For Ruby and Go developers, this constraint is critical when building concurrent IPC mechanisms or centralized loggers; writing payloads larger than 4KB to a shared IO.pipe (Ruby) or os.Pipe (Go) without external synchronization (like a Mutex) risks data corruption, forcing developers to explicitly chunk their messages or serialize access at the application layer.
_PC_PIPE_BUF
resolution in nanoseconds for file timestamps
_PC_TIMESTAMP_RESOLUTION defines the resolution of file timestamps (atime, mtime, ctime) in nanoseconds [The Open Group]. While the POSIX standard mandates a coarse minimum resolution of one second, modern Linux filesystems like ext4, XFS, and btrfs support nanosecond precision—though XFS only gained this capability in Linux 5.10, and the effective resolution is ultimately bounded by the system clock's granularity. This granularity is critical for build systems, backup utilities, and distributed synchronization, as coarser historical limits (such as FAT32's 2-second resolution) can easily cause race conditions where rapid, successive file modifications go undetected. For Ruby and Go developers, methods like File.mtime or os.Stat().ModTime() directly expose the underlying filesystem's capability; therefore, while modern local development enjoys precise change tracking, deploying applications that rely on timestamp comparisons to legacy or network-mounted filesystems requires explicit caution to avoid subtle synchronization bugs.
_PC_TIMESTAMP_RESOLUTION
number of bytes in a symbolic link
SYMLINK_MAX (_PC_SYMLINK_MAX) defines the maximum number of bytes that can be stored in the contents of a symbolic link [The Open Group]. While the POSIX/XSI standard mandates a historical minimum of just 8 bytes for _POSIX_SYMLINK_MAX, the practical limit on Linux varies by filesystem: ext4 can store targets up to PATH_MAX (typically 4096 bytes), while XFS hardcodes a 1024-byte ceiling and btrfs allows roughly 3900–4095 bytes. Notably, pathconf(_PC_SYMLINK_MAX) returns -1 without setting errno, because POSIX acknowledges that pathconf() and open() follow symbolic links, leaving no way to query a symlink's own limit . Attempting to create a symbolic link whose target exceeds the underlying filesystem's boundary causes symlink() or symlinkat() to fail with the classic ENAMETOOLONG error. For Ruby and Go developers, this constraint is generally transparent during normal filesystem operations, but it surfaces as a critical edge case when embedding encoded payloads, long base64 strings, or generated URLs directly into symlink contents as a form of lightweight metadata storage; in these scenarios, methods like File.symlink or os.Symlink will raise an Errno::ENAMETOOLONG or syscall.ENAMETOOLONG exception, forcing developers to explicitly hash, compress, or offload the target data to an external file or database.
